# Opaque case state with explicit projection and atomic action outcomes

The platform persists a generic playthrough envelope and a case-owned JSONB state document. Cases validate their state schemas, interpret actions, perform authoritative transitions, and explicitly derive the representation visible to the player. The kernel must never automatically serialize the private state document to the browser. Opaque state means the kernel ignores gameplay semantics; it does not permit arbitrary client state writes. Secrets may reside in server-only case state, case definitions/configuration, or protected assets without a separate secret-management service. Custom case SQL schemas and independent storage services are deferred.

Authoritative mutating actions carry a client-generated request ID, playthrough ID, base revision, case-owned action type, and payload. A successful durable state mutation atomically commits state, revision, emitted events, committed outcome, request ID, and an input identity/fingerprint. An identical retry returns that committed outcome without executing again; reuse of an already committed request ID with different input must be rejected. Optimistic revisions separately protect against stale writes.

Revisions advance when an action commits a durable authoritative playthrough change, including case state or first completion (ADR-0008). A single atomic transition advances once even if both change. A wrong password advances the revision if the case persists an attempt counter; without a durable change it need not advance. Malformed, unauthorized, stale, and ordinary pre-commit validation failures do not require durable idempotency records or revision advancement. Clients correct/reconcile and use a new request ID. M0 does not implement permanent request-ID binding for rejected submissions.

Replayed outcomes carry their committed revision. The frontend must keep newer known state instead of replacing it with an older snapshot, fetching current state if reconciliation requires it. This contract covers internal committed authoritative mutations in M0; external-side-effect idempotency and a generic distributed-workflow framework are deferred. Callback restrictions are specified in ADR-0004. Automatic expiry/cleanup machinery is deferred for M0.
